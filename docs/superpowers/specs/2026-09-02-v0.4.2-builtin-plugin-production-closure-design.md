# A4Diag v0.4.2 Built-in Plugin Production Closure Design

**Date:** 2026-09-02  
**Status:** Approved in chat; awaiting written-spec review  
**Target release:** v0.4.2

## 1. Purpose

v0.4.2 closes the production gap between A4Diag's tested core/plugin
components and a real controller-to-target remediation path. It does not add a
third-party plugin ecosystem. It makes the ten repository-owned built-in
plugins installable, attestable, configurable, executable, and testable from a
signed release.

The release must preserve the established safe default: a fresh install has no
targets, is read-only, does not auto-execute LOW operations, and does not make
network connections to a target until an administrator explicitly configures
one.

This design extends the generic plugin-agent design dated 2026-08-26 and the
production runtime closure design dated 2026-08-28. Where those documents
describe third-party plugin installation as a future generic capability,
v0.4.2 deliberately defers it.

## 2. Confirmed v0.4.1 gaps

The following are production defects, not missing unit-test concepts:

1. The built-in plugin wheel is installed into the application virtual
   environment, but its manifests are not staged under `/opt/a4diag/plugins`
   and the production registry remains empty.
2. Read-only `a4diag plugin list` constructs the full administrative installer
   and tries to resolve `/etc/a4diag/secrets/release-signing.key`. A release
   private key must never exist on a controller.
3. The transport manifests reference
   `/usr/libexec/a4diag/a4diag-transport-helper`, but v0.4.1 ships no such
   executable or generic target installer.
4. Plugin systemd templates exist, but the installer creates no plugin instance
   configuration and enables no sockets.
5. Capability plugin hosts currently construct `LocalFileAdapter` directly.
   Enabling those hosts on a controller for an SSH target would operate on the
   controller, not the target. This path must never be used as a remote
   remediation shortcut.
6. The transport's remote JSON omits the complete ticket context needed by a
   target-side zero-trust executor, including transaction, step, marker, undo,
   digest, expiry, and replay binding.
7. CI proves component contracts but not the signed-install -> built-in
   registry -> socket activation -> SSH helper -> target effect path.

## 3. Scope

### 3.1 In scope

- The ten existing built-in manifests: local/SSH transport, files/services/
  packages capabilities, OpenAI-compatible model, and CLI/FlashDuty/SMTP/
  webhook notifications.
- Signed controller and generic target release bundles.
- Immutable built-in artifact staging and digest-pinned registry entries.
- Keyless read-only plugin administration.
- Plugin instance configuration and systemd socket activation.
- A generic target helper and target executor with a fixed typed protocol.
- Target-specific SSH and execution-signing identities.
- Correct remote routing for prepare/apply/verify/undo/reconcile.
- LOW/HIGH gates, CLI approval/resume, rollback, reconciliation, audit, and
  reporting across the real plugin path.
- Linux CI and a release gate that exercises the complete path.

### 3.2 Out of scope

- Third-party plugin packaging, publisher trust stores, or plugin marketplaces.
- Docker, Kubernetes, Windows, or non-systemd targets.
- Raw shell/script/command execution.
- Automatic installation of the target helper over SSH.
- VM creation, deletion, cloning, snapshot, or hypervisor access.
- Automatic recovery of an unreachable or unbootable target.

Existing third-party-oriented `plugin verify/install` behavior is not a
production feature of v0.4.2. It must fail closed with a stable unsupported
status unless a later approved design supplies an asymmetric publisher trust
model. `plugin list` and `plugin disable` remain usable and do not require a
signing secret.

## 4. Architecture

### 4.1 Controller responsibilities

The controller runs the LangGraph workflow, target registry, policy, approval,
transaction, checkpoint, audit, model, notification, and transport processes.
It owns the private SSH key and the private target-operation signing key for
each registered target.

For an SSH target, capability code must not use a controller-local adapter.
The core routes each capability lifecycle request through the target's verified
transport instance. Capability manifests remain on the controller as the
contract and policy source; their implementation executes in the target
executor.

The effective remote path is:

```text
LangGraph workflow
  -> registry and policy gate
  -> target-specific transport socket
  -> fixed /usr/bin/ssh argv
  -> unprivileged target helper
  -> local AF_UNIX executor socket
  -> built-in capability implementation on the target
```

Model output never selects an executable or constructs argv.

### 4.2 Target responsibilities

The generic target bundle installs only:

- an unprivileged `a4diag-target` SSH account;
- `/usr/libexec/a4diag/a4diag-transport-helper`;
- a root-owned target executor and systemd unit/socket;
- the built-in capability implementation required by the executor;
- a controller verification public key;
- a root-owned replay/transaction ledger;
- explicit managed-resource policy.

It does not install the LangGraph controller, model plugin, notification
plugins, plugin administrator, or any VM-management capability.

The SSH key is constrained with a forced command and restrictions equivalent
to no PTY, no port forwarding, no agent forwarding, no X11 forwarding, and no
user-supplied command. The helper rejects an unexpected original command.

### 4.3 Privilege separation

The SSH helper runs without root privileges. It parses one bounded canonical
JSON request and forwards it over a local AF_UNIX socket. The root executor
performs privileged effects only after independently validating the signed
request and local policy.

The executor is not a shell and exposes no generic process API. It dispatches
only the built-in capability lifecycle methods known to its release version.

## 5. Built-in release and registry

### 5.1 Controller bundle

The controller archive contains:

- the core wheel and built-in plugin wheel;
- all ten manifests as normal release artifacts;
- a generated built-in index binding plugin name, type, version, API version,
  manifest SHA256, and artifact SHA256;
- plugin systemd units;
- settings/config schemas;
- the complete dependency wheelhouse.

`MANIFEST.json`, `SHA256SUMS`, and the existing outer RSA release signature
cover the index, manifests, wheels, installer, and units. No plugin or release
private key is copied to an installed machine.

### 5.2 Installed layout

Built-ins use a versioned runtime separate from the core runtime:

```text
/opt/a4diag/plugins/
  releases/0.4.2/
    venv/
    artifacts/a4diag_builtin_plugins-0.4.2-py3-none-any.whl
    manifests/*.json
    builtin-index.json
  current -> releases/0.4.2
  <plugin-name>.json
  artifacts/a4diag_builtin_plugins-0.4.2-py3-none-any.whl
```

The top-level manifest/artifact paths satisfy the current registry's
containment and digest checks. Plugin services execute from the versioned
plugin runtime, not the core venv. The `current` link, top-level attestations,
and registry update are switched as one recoverable installation transaction.

### 5.3 Registry behavior

A fresh install creates ten digest-pinned entries with `enabled: false`.
Nothing is started and no target is contacted.

On upgrade, the installer preserves an administrator's enabled/disabled
choices while replacing built-in version and digest fields with the verified
new release values. It takes a byte-for-byte registry snapshot before the
switch. If self-check or a previously enabled plugin health check fails, it
restores the old plugin runtime link, registry, manifests, and service state.

Read-only plugin commands load only the registry and public release metadata.
Administrative mutation commands require local administrator authorization,
but never a release-signing private key.

## 6. Instance configuration and initialization

Plugin instances live under `/etc/a4diag/plugins/<instance>.yaml`. Their names
are safe identifiers; a transport instance may be target-specific while its
manifest remains `transport-ssh`.

`a4diag init` is one recoverable configuration transaction:

1. Strictly parse settings v3 and reject unknown fields.
2. Validate that every requested plugin is a verified built-in.
3. Stage instance files with root ownership and minimum group readability.
4. Enable/start only the requested sockets.
5. Probe the model, notifications, and every target identity.
6. Pin SSH host key, machine-id, OS identity, and systemd identity.
7. Atomically commit config, instance files, registry flags, and service state.
8. Restart the core and run an offline self-check plus plugin health checks.
9. Restore the prior bytes and service state on any failure.

Non-interactive initialization cannot enable writes from a boolean alone. The
request must contain the exact literal `write_confirmation: "ENABLE"`; the
confirmation is consumed and is not persisted as reusable authority.

## 7. Remote request and key model

### 7.1 Per-target keys

Each target uses two independent key pairs:

- an SSH key pair for transport authentication;
- an asymmetric operation-signing key pair for executor authorization.

The controller stores both private keys as target-scoped 0600 secrets. The
target stores only the SSH public key and operation-verification public key.
Compromise of a target therefore cannot mint a new controller-authorized
operation.

The bootstrap command creates material locally and emits a generic target
configuration bundle. An administrator copies and installs that bundle on the
target. A4Diag never grants itself target privileges over an untrusted channel.

### 7.2 Signed envelope

Every effect envelope binds at least:

- protocol and release version;
- controller and target identifiers;
- target identity fingerprint;
- transaction ID, step ID, lifecycle method, and idempotency key;
- normalized operation and parameters;
- marker and undo data when applicable;
- plan digest and effect-payload digest;
- effective risk and approval ID for HIGH operations;
- issued-at, expires-at, and single-use nonce.

The signature covers canonical JSON bytes. Unknown fields, duplicate JSON
keys, non-canonical encodings, expired requests, digest mismatches, identity
mismatches, release/API mismatches, and repeated nonces are rejected before
dispatch.

Read-only identity and bounded evidence requests use a separate narrow method
surface and are authorized by the forced SSH identity and target policy. They
cannot be upgraded into an effect request.

## 8. Capability constraints

### 8.1 Files

`files.replace_managed_file` and `files.set_mode` operate only below explicit
administrator-managed roots. Each path component is checked with `lstat`;
symlinks, devices, traversal, and non-regular final files are rejected.
Markers preserve the bytes, mode, uid, gid, and digest required for exact
restoration. Writes use same-directory temporary files, fsync, and atomic
replace.

### 8.2 Services

Service operations accept validated full systemd unit names and fixed
`systemctl` argv templates. Markers preserve active, sub, unit-file, and
invocation state. Verification and reconciliation query the target again;
they do not trust process exit status alone.

### 8.3 Packages

Package operations require an exact package name, version, and approved
repository. They are always at least HIGH. Fixed non-interactive dnf/apt/rpm/
dpkg templates are used. Undo restores a prior artifact only when that exact
artifact is still available; otherwise the system reports a truthful partial
or unavailable rollback.

Package allowlists reject packages that would alter the protected control
plane. v0.4.2 assumes configured official repositories; it does not claim that
an arbitrary malicious package can be made safe by a package-name allowlist.

### 8.4 Permanent protected surface

Neither LOW classification nor human approval can authorize:

- raw command, shell, script, argv, cmd, or exec input;
- SSH daemon/configuration, authorized keys, PAM, sudoers, or target keys;
- network interfaces, addresses, DNS, routes, firewall, or packet filtering;
- the helper, executor, public key, replay ledger, or A4Diag policy;
- users/groups, cron, kernel, SELinux, or equivalent security foundations;
- libvirt, qemu, virsh, hypervisor APIs, or VM lifecycle operations;
- an unregistered target or a target whose pinned identity changed.

Protected paths and operation classes are checked in core policy and again in
the target executor. An overly broad managed root such as `/etc` does not
override the protected list.

## 9. Risk, approval, execution, and recovery

Effective risk is the maximum of model judgment, critic judgment, manifest
risk floor, target override, and core rule. The model may raise but never lower
the enforced risk.

LOW executes automatically only when both global and target
`auto_execute_low` are explicitly true and every identity, allowlist,
reversibility, budget, and lock check passes. HIGH creates a durable pending
approval and has zero effect dispatch before approval.

Approval displays the target identity, full typed operations, equivalent fixed
command representation, risk reasons, resources, verification, rollback,
expiry, and plan digest. CLI approval re-probes identity and configuration,
uses the same approval/checkpoint databases as the runtime, and resumes the
same transaction. Any material change invalidates approval.

Lifecycle order is prepare -> apply -> verify. A failed verification rolls
back completed steps in reverse order and verifies each undo. A timeout,
transport loss, or process crash after possible dispatch becomes
`execution_unknown`; it is never replayed blindly. Reconciliation classifies
the real state as not-applied, applied, partial, or unknown before any further
action. Unknown and unreachable states stop for human handling.

## 10. Notification and reports

CLI notification is always available. FlashDuty, SMTP, and webhook are
optional built-ins. They distribute approval information but do not approve an
operation.

Every channel receives redacted target, digest, risk, typed operation,
equivalent fixed command, verification, rollback, and residual-risk fields.
Secrets enter only the channel-specific transport credential field. Required
notification failure blocks approval; optional notification failure remains an
audited warning.

Reports persist the runtime result and all lifecycle outcomes. A process
restart must neither discard an accepted alert nor repeat a completed effect.

## 11. Release assets and installation

GitHub Release contains:

```text
install-a4diag.sh
a4diag.tar.gz
a4diag.tar.gz.sig
install-a4diag-target.sh
a4diag-target.tar.gz
a4diag-target.tar.gz.sig
a4diag-release-public.pem
```

Both archives have complete internal manifests and are independently signed by
the release key. Bootstrap scripts pin the expected public-key fingerprint,
verify the outer signature and exact internal inventory, stage into a new
version directory, then perform an atomic switch. A failed verification or
health check leaves the old version active.

The target installer is generic. It contains no `t_11`, fixed IP, controller
address, or environment-specific profile. Target identity, controller public
key, source-address restriction, and managed resources arrive through an
administrator-reviewed input file.

## 12. CI and release gates

Before `v0.4.2` is tagged, GitHub Actions must pass:

1. `python -m compileall -q src packages tests tools`.
2. The complete pytest suite on Linux, with no Windows-only claim standing in
   for POSIX behavior.
3. Source and assembled-release verification.
4. The supported Linux installation matrix, including Alibaba Linux 3.
5. A fresh signed install where `plugin list --json` returns exactly ten
   disabled built-ins without resolving a private signing key.
6. Manifest/artifact/index tamper and extra-file rejection.
7. Plugin systemd socket activation and restart behavior.
8. A disposable SSH target running the signed target helper/executor bundle.
9. Identity probe and bounded read through fixed SSH argv.
10. A LOW managed-file change, independent verification, forced failure, and
    exact rollback.
11. A HIGH package plan with zero dispatch before approval and dispatch only
    after digest-bound approve/resume.
12. Host-key/machine-id drift, expired signature, replay, wrong target,
    protected path, raw execution field, timeout, and crash rejection.
13. Restart recovery proving that an ambiguous or completed effect is not
    automatically replayed.
14. Upgrade failure proving byte-for-byte config/registry restoration and old
    runtime availability.

Publish runs only after the commit on `main` passes these gates. The annotated
`v0.4.2` tag and release assets are then created, downloaded again, hashed,
signature-verified, and smoke-installed by the release workflow.

## 13. Real deployment acceptance

CI and release work do not authorize contact with real servers. After release,
an administrator performs the real acceptance in this order:

1. Upgrade the controller and verify config preservation, self-check, registry,
   service stability, and ten built-in entries.
2. Install the generic target bundle manually on the disposable test target.
3. Register it read-only and verify host key, machine-id, OS, and systemd.
4. Exercise read-only diagnosis and persistent reporting.
5. Enable writes only for one disposable managed directory and test LOW
   repair, verification, and rollback.
6. Test a HIGH operation, notification, CLI approval, and explicit resume.
7. Attempt protected SSH/network paths and a different target; require policy
   denial and zero effect dispatch.
8. Expand managed resources only after all evidence passes.

If the target becomes unreachable or unbootable, A4Diag reports the condition
and stops. It receives no VM-management permission.

## 14. Completion criteria

v0.4.2 is complete only when:

- the signed installer produces a usable, digest-pinned built-in registry;
- read-only plugin administration never requests a private signing key;
- the helper/executor bundle is present, signed, installable, and generic;
- SSH target effects run on the target and never through a controller-local
  `LocalFileAdapter`;
- complete transaction/ticket/marker/undo data reaches the executor;
- permanent protected surfaces are denied in both controller and target;
- LOW/HIGH, approval, resume, rollback, reconcile, audit, and restart behavior
  pass the real plugin path;
- all Linux release gates pass;
- published assets can be independently downloaded and verified;
- no real target is modified before the separate administrator acceptance
  steps.
