# A4Diag v0.5.0 发布说明

v0.5.0 接通服务异常与 HTTP 接口恢复闭环：采集授权证据、校验模型决策、执行受控操作，再独立验证业务是否恢复。

## 主要变化

- 采集管理员登记的服务状态、日志和受管文件；模型可按证据 ID 请求补采，最多两轮。读取范围、输出大小和超时由程序限制。
- 模型收到结构化响应 Schema、操作参数、授权资源和证据目录。证据不足、低置信度、输出错误或审查不完整时停止写入。
- 执行后重新检查服务状态及配置的 HTTP 健康接口，全部通过才报告成功。失败进入回滚，报告分别保留业务恢复和回滚结果。
- 插件通过 systemd 独立凭据读取密钥；修复动态账户、目标连接权限、安装目录及升级重启问题。
- 控制端、内置插件和目标端版本统一为 0.5.0，不能与 0.4.3 包混装。

## 兼容性变化

**控制端要求 systemd 247 或更新版本。** Ubuntu 22.04/24.04、Debian 12、Rocky Linux 9、AlmaLinux 9 在安装验证范围内。Alibaba Cloud Linux 3、Rocky/AlmaLinux 8 的旧版 systemd 不满足控制端要求，安装器会拒绝；CI 对这些控制端环境验证的是拒绝行为。

目标端单独验证 Alibaba Cloud Linux 3、Rocky Linux 9、Ubuntu 24.04 和 Debian 12。目标端仍需要 systemctl、journalctl 和 Python 3.11。

旧配置未登记 `recovery_checks` 时，不再允许自动写入。HTTP 检查由控制端发起，地址必须从控制端可达；当前不支持需鉴权的健康接口，也不跟随重定向。

## 从 v0.4.3 升级

1. 暂停新修复请求，将控制端设为只读；先处理未完成事务，备份配置、密钥及持久化状态。
2. 确认控制端 `systemctl --version` 满足 247+。旧系统应先迁移控制端，不能通过跳过安装检查来获得兼容性。
3. 先升级所有受控目标端到 0.5.0，并确认目标执行器 socket 正常；再升级控制端及内置插件到同一版本。
4. 按[闭环配置指南](../deployment/service-http-recovery.md)登记服务、证据源和恢复检查，使用 `a4diag init --input` 重新生成插件配置和凭据授权。旧插件实例不会仅因替换 wheel 就自动获得新配置。
5. 检查模型密钥和目标连接密钥的账户及权限。生产密钥由 `a4diag` 持有，普通密钥文件权限为 `0600`；不要把密钥放进初始化 JSON。
6. 保持只读完成模型探测、目标身份和证据采集检查，再在测试服务上验证修复成功、HTTP 未恢复时回滚两条路径，最后恢复所需写策略。

HIGH 风险操作仍需人工审批和明确恢复执行。不要把 `rollback_succeeded` 当作业务恢复成功；业务成功必须有 `recovery_result.ok=true`。

## 安装包与验证

Release 包含控制端和目标端归档、各自签名、一键安装脚本和发布公钥。安装器先验证归档签名，再验证内部清单。

分支 CI 覆盖单元、契约、集成测试，真实 systemd/SSH 端到端闭环、构建和发行版安装检查。模型测试使用实际插件连接本地协议响应服务，不代表任何外部模型已在真实生产故障上通过质量评估。

详细流程、模型接入及配置示例见[服务异常与 HTTP 恢复闭环](../deployment/service-http-recovery.md)。
