# A4Diag v0.4.0 known limitations

These limitations are stated without weakening the safety guarantees.

## Platform

- **No Docker, Kubernetes, or non-systemd hosts.** The unit inventory,
  installer, and smoke tests target systemd on the supported
  Rocky/AlmaLinux/RHEL/Ubuntu/Debian versions only.
- **No automatic VM rebuild.** Disposable test environments are provisioned by
  the operator; the suite never creates, rebuilds, or destroys VMs by itself.
- **Windows is a development/test platform only.** POSIX permission, owner,
  symlink, AF_UNIX, and systemd gates (and the bash installer harness) run on
  the Linux CI matrix; on Windows they skip with explicit reasons.

## Trust and recovery

- **Administrator trust of installed execution plugins.** A capability plugin
  registered by an administrator runs with the permissions its manifest
  declares; the agent does not sandbox the plugin process beyond the systemd
  unit isolation and the declared `permissions`/`network_access`/`secret_refs`.
- **No remote recovery of an unreachable or destroyed target.** If the target
  cannot be reached or has been reimaged, the agent reports
  `target_identity_unavailable` / `policy_denied` and requires operator
  re-registration; it never re-registers or re-runs automatically.
- **CLI approval is required for every HIGH operation.** There is no
  auto-approval path; a high-risk-floor operation stays HIGH even when the
  model claims LOW.

## Operational

- **Unknown executions stop.** When an effect outcome cannot be determined,
  the transaction stops as `execution_unknown` and is reconciled (never
  replayed); a human decides the next step.
- **Reports classify v3 action reports as abnormal** under the legacy reader
  (status vocabulary changed); old v0.3 reports remain readable.
- **Notifications depend on registered plugins.** No mail/webhook/FlashDuty
  delivery is performed by the core; notification plugins must be registered
  and their delivery is a plugin concern.
- **The capability executor is wired over the plugin RPC sockets; the
  collector, model, and notification ports still raise fail-closed until
  their plugin hosts expose the corresponding methods.** `a4diag serve`
  (the `a4diag-core.service` command) and `a4diag-plugin --instance %i`
  (the `a4diag-plugin@.service` command) exist and compose the production
  runtime; a default install with no targets starts and stays read-only.
  Live socket connectivity, transport hosts, and model/notification hosts are
  the remaining production integration steps (documented in the deployment
  docs and checklist).
