# A4Diag v1.0.0

v1.0.0 将 Linux 服务与文件的受控修复、结构化证据采集、模型决策和独立恢复验证整合为同一条事务链路。控制端、内置插件和目标端统一使用 1.0.0。默认仍为只读。

## 能力与变化

- 支持管理员登记的文件系统容量、内存、负载、文件属性/摘要、软件包状态、TCP、DNS 七类 Linux 探针；保留服务状态、日志和 HTTP 检查。
- 探针只通过精确 ID 授权，结果绑定完整定义摘要；两端定义不一致、截断、类型错误、采集失败或超时均不能通过恢复验证。
- 每次修复后重新采集实际状态，按管理员配置的条件判断恢复；模型不能自己宣布业务恢复。
- 文件权限及受管文件内容修复、服务操作继续使用签名票据、身份绑定、风险审批、prepare/apply/verify/undo/reconcile 和审计链。
- 模型输出预算默认 8192，可配置 64–16384；模型超时默认 120 秒，可配置 1–300 秒。
- 修复目标服务重启丢失 socket，以及旧版本升级后监听端点未重新绑定的问题。
- TCP 探测区分远端连接失败与本机资源/权限错误，避免错误满足负向恢复条件。

## 支持边界

本版不是任意 Linux 命令执行器。磁盘、资源、软件包和网络探针提供诊断与验证，不自动授予磁盘清理、杀进程、安装软件包或修改网络配置权限。当前加固安装器不开放软件包写入。复杂故障缺少证据或受支持操作时，需要管理员介入。

Python 3.11、x86_64 Linux；控制端要求 systemd 247+。控制端支持矩阵、明确拒绝的旧版 systemd 环境及目标端矩阵见 [安装指南](https://github.com/zhuzihan60/agent/blob/v1.0.0/docs/install.md)。

## 升级与模型接入

1. 暂停新写请求，将控制端设为只读；备份配置、密钥和状态，先核实未完成事务。
2. 先升级目标端，再升级控制端和内置插件，三者保持同版本。目标端安装仍需管理员提供初始化配置。
3. 在两端登记完全一致的探针定义，并使用原始初始化输入重新运行 `a4diag init --input /安全路径/init.json`，生成对应插件配置。旧版不能解析本版探针响应，避免混用。
4. 保持只读确认身份、连通性与采集结果，然后在限定演示资源上验收修复，再启用需要的写策略。

两端安装说明见 [安装指南](https://github.com/zhuzihan60/agent/blob/v1.0.0/docs/install.md)，模型 Base URL、模型名、密钥引用及预算配置见 [模型与服务恢复配置](https://github.com/zhuzihan60/agent/blob/v1.0.0/docs/deployment/service-http-recovery.md)，探针条件见 [Linux 配置示例](https://github.com/zhuzihan60/agent/blob/v1.0.0/docs/linux-fault-recovery.md)。

## 验证与发行资产

发布流水线要求全量单元、契约、集成和验收测试，真实 systemd/SSH 链路及 socket 生命周期回归，控制端与目标端发行版安装检查全部通过。归档和内部清单均签名；一键安装器验证签名和文件摘要后才安装。

Release 提供 `a4diag.tar.gz`、`a4diag-target.tar.gz`、两份归档签名、两端安装脚本与验证公钥。详细人工故障验收记录随源码的发布验收计划保存。
