# Migration guide: v0.3 fixed-target runtime → v0.4 generic plugin runtime

Applies to every deployment that ran the v0.3 fixed-target runtime
(`t_01` + fixed IP + frozen systemd unit allowlist + hardcoded read-only SSH
user).

## What changed

- **No fixed targets.** v0.3 shipped a single hardcoded target (`t_01` at a
  fixed IP with a frozen unit allowlist). v0.4 removed that behavior: targets
  are registered by id in the v3 settings file, and every alert / MCP tool /
  collector path resolves a target **only by its registered id**.
- **No IP matching.** Alertmanager labels, MCP tool calls, and policy
  authorization never match by IP address or hostname, and never fall back to
  the first configured target.
- **No hardcoded SSH user.** The read-only SSH user is explicit in the legacy
  compatibility config (`ssh_user`); nothing is hardcoded in source.
- **MCP/collector on the v3 runtime.** The read-only MCP surface is generated
  from the pinned plugin registry and collects evidence through the v3
  runtime's collector port (verify identity → acquire read view → collect).
- **Old permissions are never auto-converted.** v0.3 frozen target settings,
  unit allowlists, and IP allowlists are **not trusted and not imported** into
  v3 settings automatically. `AgentSettings` accepts only the v3 schema; there
  is no conversion path from the legacy `Config`.
- **Old reports stay readable.** The report reader (`classify_report`,
  `cleanup_expired`, on-disk YAML layout) is unchanged, so v0.3 reports remain
  readable and retain their retention policy.

## Required migration steps (in order)

1. **Back up the old configuration and state.**

   ```bash
   sudo cp -a /etc/a4diag /var/backups/a4diag-v0.3-$(date +%F)
   sudo cp -a /var/lib/a4diag /var/backups/a4diag-state-v0.3-$(date +%F)
   ```

   Keep the v0.3 config offline; it is not read by v0.4.

2. **Run `a4diag init` to create a fresh v3 settings file.**

   ```bash
   sudo a4diag init --output /etc/a4diag/config.yaml
   ```

   The generated file defaults to `global_mode: read_only`, `targets: []`,
   `plugins: []`. Do not copy target blocks from the v0.3 config — they are
   not compatible and are never converted.

3. **Register each target individually.**

   For every machine that was previously covered by a fixed target:

   ```bash
   sudo a4diag init --input /path/to/target-request.json
   ```

   - Assign a fresh target id (`target-1`, …) — the old `t_01` id is not
     special and carries no permissions.
   - Grant only the capability actions the machine actually needs; select new
     allowlists (unit allowlists, file resources, …) from the registered
     plugin manifests. Old v0.3 frozen allowlists are not imported.

4. **Verify identity (machine-id / host key) before enabling anything.**

   The runtime refuses to start a write transaction until the target's live
   identity probe matches the registered fingerprint:

   ```bash
   sudo a4diag approvals list --json        # read-only status of any pending work
   ```

   - Confirm each target's `machine-id` / SSH host key matches the fingerprint
     recorded at registration time. A mismatch is `policy_denied` /
     `target_identity_unavailable`, never an automatic re-registration.

5. **Run read-only acceptance first.**

   - `global_mode: read_only`, `auto_execute_low: false`.
   - Generate test alerts carrying the new registered `target_id` label and
     confirm the runtime returns `read_only` / `read_only_no_model` /
     `policy_denied` reports with **zero** plugin write calls.
   - Drive the read-only MCP surface and confirm every tool call resolves only
     registered target ids.

6. **Explicitly enable writes only after acceptance.**

   Only when read-only acceptance passes for every target:

   ```bash
   sudo a4diag init --input /path/to/write-enable-request.json   # global_mode: read_write
   ```

   - `write_enabled` requires the literal `ENABLE` confirmation during init.
   - HIGH-risk operations still require a digest-bound CLI approval; unknown
     executions are never replayed automatically.

## Rollback

- Restore the backed-up v0.3 config and state from step 1, then reinstall the
  v0.3 package. v0.4 never writes into v0.3 config/state paths, so the backup
  remains intact.
- v0.4 reports are readable by the v0.3 reader only if the v0.3 report schema
  is preserved; v0.4 action reports use the v3 status vocabulary and classify
  as abnormal under the legacy reader — treat them as informational.

## Never do

- Never hand-edit the v3 settings file to graft v0.3 target blocks or unit
  allowlists into it.
- Never route an alert/MCP call by IP or by "first configured target".
- Never set `global_mode: read_write` before the read-only acceptance pass.
